# 10 分钟产品演示讲稿 / 10-minute demo script (v1.0.0)

**主线：** 企业申请 → 风险评估 → 授信 → 还款 → 逾期 → 预警 → 处置 → 结果反馈 → 模型更新。

一句话开场：**DAIBM-SCF 是一个供应链金融 AI 风险管理平台原型。一笔融资从申请到结清的每一步都能追溯到做决策的模型版本、
训练数据和操作人；AI 模型只有通过独立验证才能上线，而且可以审批、可以回滚。**

演示数据说明见 [DATASET_OVERVIEW.md](DATASET_OVERVIEW.md)，截图见 [../product/screenshots/](../product/screenshots/)。
界面默认俄语，演示前点击右上角 `中文` 切换。

## 演示前准备（提前 10 分钟）

```bash
scripts/ops/init-env.sh                          # 仅首次：生成 .env（随机数据库密码与演示密码，会打印演示密码）
docker compose -p daibm-scf-mvp up -d --build    # 空数据卷约 30 秒 healthy，演示数据自动生成
curl -s http://127.0.0.1:8010/api/v1/ops/health  # "status":"ok"
scripts/ops/backup.sh demo-baseline              # 冻结演示起点，演示结束后用它恢复
```

Windows：双击 `start-demo.cmd`，它会生成 `.env`、启动服务并打印演示密码。

- 所有账号的密码都是 `.env` 中的 `DAIBM_DEMO_PASSWORD`。
- 建议用 3 个独立的浏览器配置文件（或 3 个不同的浏览器）同时保持登录，省去切换账号的时间：
  **A** `admin.demo`，**B** `risk.demo`，**C** `auditor.demo`。企业用户、核心企业和融资方在第 4 个窗口里通过“退出 → 点击角色卡片”切换，每次约 5 秒。
- 可选检查：`python scripts/defense_preflight.py --base-url http://127.0.0.1:8010`（只读：健康、页面、文档、五个角色登录）。

## 第 1 分钟 · 登录与角色（0:00–1:00）

**操作**
1. 打开 `http://127.0.0.1:8010`，停在登录页（[截图 01](../product/screenshots/01-login.png)）。
2. 点击“管理员”卡片，输入密码并登录 `admin.demo`，进入风险驾驶舱。
3. 依次切到窗口 B（`risk.demo`）和窗口 C（`auditor.demo`），展示不同角色的左侧导航。

**讲解要点**
- 平台有六个角色：企业用户（供应商、核心企业）、融资方、风险经理、审计员、管理员。今天重点看管理员、风险经理、审计员和企业用户。
- 每个账号都有自己的服务端会话，这不是前端切换角色。越权请求由 API 拒绝，并记录为安全事件。
- 数据按组织隔离：企业只能看到自己的融资；审计员只能看到被授权的放款机构；管理员可以看全部组织。

## 第 2–4 分钟 · 业务流程：申请 → 审批 → 放款（1:00–4:00）

**操作**
1. **企业用户** `supplier.normal.demo`（稳健制造）→ **业务工作台** → 新建申请：
   - 核心企业 `CORE-001`；放款机构 `BANK-001`（只有一家放款机构时自动选中）；
   - 合同号 `DEMO-LIVE-001`，金额 50000，期限 90 天，风险因素保持默认；
   - 点击“保存草稿”，再点“提交申请”。
2. **核心企业** `core.demo` → 打开这笔申请 → 填写“确认的应付上限”（不低于金额）→ 点击“确认交易”。
3. **融资方** `financier.demo` → 点击“执行风险评估”：
   - 申请详情显示基线分数和校准后的分数；
   - “风险决策”面板显示使用的模型 `calibration:controlled_demo@v1`、数据快照、输入哈希和 Scope 校验结果；
   - 选择“批准”。
4. **风险经理**（窗口 B）点击“记录控制措施”；**审计员**（窗口 C）点击“完成审计”。
5. **融资方** → **融资生命周期** → 创建融资设施：
   - 填写已批准申请 ID、本金 50000、两期各 25000；
   - 点击“创建还款计划”，再依次点击“发起放款”和“确认放款”，状态变为 `active`。

**讲解要点**
- 申请提交时就绑定放款机构，之后不能更换。这决定了谁能看到这笔申请，以及用哪家机构的模型评估它。
- 风险评分由**本机构的 ACTIVE 模型**校准；没有激活模型时回退到透明基线，并记录回退原因。
- 每一步都有版本号：并发修改会被拒绝，每次状态转移都写入哈希链账本。
- 放款和还款是**受控模拟**，不会发起真实银行转账。

**时间不够时：** 做完第 3 步后，直接在融资生命周期里打开稳健制造的 `DEMO-NORMAL-001` 卷宗，展示已完成的放款、两期还款和结清。

## 第 5 分钟 · 风险事件：评分、预警、任务（4:00–5:00）

**操作**（窗口 B，`risk.demo`）
1. **风险驾驶舱**（[截图 02](../product/screenshots/02-risk-dashboard.png)）：
   - 资产：40 笔融资，297,000 放款，120,000 余额；
   - 风险分布：正常 21、高风险 1、违约 18；
   - 损失：回收 15,000、核销 62,000、回收率 19.5%；
   - 当前 ACTIVE 模型，以及未关闭的预警。
2. **风险预警中心**，状态筛选 `PROCESSING`（[截图 03](../product/screenshots/03-alert-center.png)）：
   - 东方物流“逾期 35 天，达到阈值 30 天”，严重程度 HIGH；
   - 处理历史：创建 → 指派 → 处理中；
   - 预警下已关联一项催收任务。
3. **风险任务中心**（[截图 04](../product/screenshots/04-task-center.png)）：“Collect the overdue installment”状态为 IN_PROGRESS。现场添加一条处理备注。
4. **风险详情**，选择东方物流（[截图 05](../product/screenshots/05-risk-detail.png)）：
   - 风险分类“高风险”，评分 0.467；
   - 模型 v1、工件哈希、训练快照；
   - 完整生命周期，以及预警、任务和审计的合并时间线。

**讲解要点**
- 规则中心维护版本化的阈值规则，由后台每 60 秒扫描一次，也可以点“运行规则检测”手动触发。
- 预警的流转是 指派 → 处理 → 解决 → 审核关闭，审核人不能是处理人本人。

## 第 6–7 分钟 · AI 治理：模型版本、数据快照、决策血缘（5:00–7:00）

**操作**（窗口 C，`auditor.demo`）
1. **模型中心**（[截图 06](../product/screenshots/06-model-center.png)）：
   - 当前激活的是 `@v1`：训练 32 条结果，时间外验证 Brier 从 0.1386 降到 0.0275，晋升原因 `gate_passed`；
   - 待激活候选 `@v2`：39 条结果，Brier 从 0.1865 降到 0.0610；
   - 点击 v1 查看注册表历史：草稿 → 评估中 → 候选 → 激活；
   - 下方的 Scope 兼容矩阵说明受控演示模型不能服务 `external_verified` 请求。
2. 在 v1 详情里点击“训练数据快照”，进入**数据快照**（[截图 07](../product/screenshots/07-dataset-snapshot.png)）：
   - 快照纳入 32 条、排除 0 条；
   - 每条结果都有修订号、审核状态、原始评分和是否违约；
   - 快照不可变，数据集有哈希。
3. **决策血缘**：打开第 2 分钟新建的申请（或东方物流 `DEMO-WATCH-001`）→ 风险决策 → 点击数据快照。追溯路径是 决策 → 模型 v1 → 快照 → 32 条训练结果。
4. （可选）在模型中心对 v2 点击“激活”：
   - v2 成为 ACTIVE，v1 退役；
   - 可以“回滚到上一版本”；
   - 每次状态转移都记录操作人和原因。

**讲解要点**
- 闭环是这样的：业务结果进入结果治理（可复核、排除、恢复和替代修订），接着生成训练资格和不可变快照，然后后台 worker 训练校准模型。
  新模型必须通过**独立的时间外验证**才会成为候选，并由审计员人工激活，或者在配置允许时自动激活。
- 每家放款机构只用自己的业务结果训练模型，也只用自己的 ACTIVE 模型做决策；数据库层拒绝跨机构的数据血缘。

## 第 8 分钟 · 异常处理：逾期、追偿、核销（7:00–8:00）

**操作**（`risk.demo` 或 `financier.demo` → **融资生命周期**）
1. 打开西部化工的 `DEMO-DEFAULT-001` 卷宗，时间线依次是：
   - 逾期 95 天 → 风险处置 `ARREARS_WORKOUT` → 认定违约 `PAYMENT_DEFAULT`；
   - 启动追偿 `LEGAL_RECOVERY` → 登记担保人回款 15,000.00；
   - 核销余额 45,000.00 `UNCOLLECTIBLE_BALANCE` → 审计员结清。
2. 打开东方物流卷宗（`overdue`）：“当前角色操作”区只显示当前角色能执行的下一步。风险经理看到“发起风险处置”，企业用户 `supplier.watch.demo` 看到“提交还款”，融资方此时没有可执行的操作。
3. 回到风险预警中心，筛选 `OPEN`：西部化工的 4 条预警，其中 1 条 CRITICAL 违约，3 条 HIGH（逾期、风险处置、模型评分 0.9474）。

**讲解要点**
- 每一步都要求原因代码和证据哈希；金额精确到分，放款、还款、回收、核销始终对得上账。
- 结清后，审计员录入“业务结果”（违约或未违约），这就是模型训练用的反馈。西部化工和稳健制造的结果已经进入 v2 的训练快照。

## 第 9 分钟 · 审计：审计账本与历史记录（8:00–9:00）

**操作**（窗口 C，`auditor.demo`）
1. **可信审计账本** → 点击“立即验证”：哈希链有效，约 970 条事件。
2. （可选）点击“模拟篡改”，系统定位到被改动的事件，再点“恢复演示账本”；这次篡改和恢复都会记录为完整性事件。
3. **风险详情** → 审计表：一笔融资的申请、生命周期、预警、任务事件按时间合并展示，每条都有操作人、角色和原因。
4. **平台管理** → **安全事件**（审计员只读）：登录成功与失败、账号锁定、越权访问（403）、管理员操作。**配置中心**：每个配置项的版本、修改人和原因，回滚时生成新版本。

**讲解要点**
- 历史记录不可改写：更正通过替代修订完成，回滚通过生成新版本完成，原记录都保留。
- 审计员的可见范围由管理员授予（`audit_grants`）。

## 第 10 分钟 · 运维：健康检查、备份、恢复（9:00–10:00）

**操作**
1. 窗口 A `admin.demo` → **平台管理**（[截图 08](../product/screenshots/08-admin-console.png)）→ **运维监控**：
   - 应用、数据库和迁移版本（`20260930_0021`）；
   - 校准 worker 与风险监控的心跳；
   - 请求数、错误数和平均耗时，以及业务计数。
2. 终端执行 `scripts/ops/backup.sh demo-live`：
   - 同一快照内导出全部表、审计数据和模型工件；
   - `manifest.json` 记录每个文件的 SHA-256、行数、迁移版本和账本链头哈希。
3. 终端执行 `scripts/ops/restore.sh demo-baseline --yes`（约 20 秒，结束后自动重启应用）：
   - 恢复到演示开始前的状态，第 2 分钟新建的申请随之消失；
   - 恢复前校验文件哈希；恢复后行数、迁移版本和链头哈希必须与备份一致，账本也要重新校验通过，否则命令失败。

**讲解要点**
- 两个容器都配置了健康检查和 `restart: unless-stopped`：进程崩溃后自动拉起，会话保存在数据库中，用户不会掉线。
- 代码中没有固定密码或密钥；`POSTGRES_PASSWORD` 缺失时服务拒绝启动。

## 重置演示数据

| 场景 | 做法 |
|---|---|
| 演示结束后回到初始状态（推荐） | `scripts/ops/restore.sh demo-baseline --yes`，恢复演示前冻结的备份 |
| 完全从头开始（Windows） | `reset-defense-demo.cmd`：输入 `RESET DEMO` 确认后删除数据卷、重新启动并运行预检；演示数据集在启动时重新生成 |
| 完全从头开始（Linux） | 先备份，再执行 `docker compose -p daibm-scf-mvp down --volumes` 和 `docker compose -p daibm-scf-mvp up -d`。注意：这会**删除全部数据**，只用于演示环境 |

## 常见问题

- **看不到某笔申请或融资**：它属于其他组织，或者还没有进入你这个角色负责的阶段。
- **登录返回 423**：连续失败次数过多，账号被临时锁定。可以等锁定结束，或由管理员在“组织与用户”中先停用、再启用该账号。
- **风险评估显示“基线”**：本机构还没有 ACTIVE 模型，或者请求的 Scope 不兼容。回退原因记录在风险决策中。
