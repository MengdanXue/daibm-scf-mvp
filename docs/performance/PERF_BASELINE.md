# 性能基线 / Performance baseline (v1.0.0)

基础验证，不是压力测试。脚本：`scripts/perf_baseline.py`（在临时数据库中构造数据、测量、删除数据库），
原始结果：`docs/performance/perf_baseline.json`。

## 数据规模

| 项目 | 数量 | 构造方式 |
|---|---|---|
| 融资 facility | 1000 | 800 笔已结清（批量写入与服务相同的行，数据库完整性触发器照常校验）+ 200 笔经 `FacilityService` 放款，其中 50 笔经服务标记逾期 |
| 业务结果 outcome | 5000 | 800 条结果修订链（每笔 6–7 个修订，最新修订为有效结果） |
| 审计事件（哈希链账本） | 10002 | 服务产生的事件 + 按哈希链追加至 ≥10000 |
| ACTIVE 模型 | 1 | 校准 worker 基于有效结果训练并自动激活 |

环境：单机 Docker 中的 PostgreSQL 17，应用与数据库同机；每项操作先预热一次，再运行 5 次，取中位数与最大值；
查询数为单次操作发出的 SQL 语句数（SQLAlchemy `before_cursor_execute` 计数）。

## 结果

| 操作 | 中位数 (ms) | 最大 (ms) | SQL 语句数 |
|---|---:|---:|---:|
| 风险驾驶舱（risk_manager） | 155.0 | 191.0 | 16 |
| 风险驾驶舱（admin） | 121.0 | 222.6 | 16 |
| 风险详情（逾期融资） | 34.3 | 34.5 | 37 |
| 预警扫描（首次，产生 50 条预警） | 333.3 | 333.3 | 359 |
| 预警扫描（稳态，无新预警） | 19.2 | 21.0 | 9 |
| 模型查找（决策时 ACTIVE 模型 + 工件校验） | 61.4 | 75.9 | 1 |
| 模型注册表列表 | 5.7 | 11.6 | 4 |
| 业务结果列表（200 行） | 47.4 | 52.0 | 1 |
| 训练资格预览（全部 5000 条结果） | 637.3 | 718.9 | 2 |

驾驶舱查询数与数据规模无关（固定 16 条）；稳态预警扫描为固定 9 条；结果列表为单条查询。

## 明显瓶颈

1. **训练资格预览（~640 ms）**：对每条结果计算最新纠正、审核状态与规则原因（相关子查询），随结果数线性增长。
   它只在治理页面按需调用；需要时可改为按页返回或物化最新审核状态。
2. **决策时模型查找（~60 ms）**：数据库查询只有 1 条，时间主要花在每次决策都重新读取并校验校准工件（SHA-256 与
   结构校验）。这是有意的安全设计（不信任已缓存的工件）；如需提速，可按工件哈希缓存已校验结果。
3. **首次预警扫描（359 条语句）**：每条新预警写入预警、事件与账本记录；新预警数量决定开销，稳态扫描很便宜。
4. **风险详情（37 条语句）**：按区块（企业、融资、风险、模型、生命周期、审计）分别查询；在 35 ms 内完成，暂无需优化。
5. **驾驶舱（120–155 ms）**：在应用层汇总 1000 笔融资的状态与余额；数据量再增加一个数量级时，可下推为 SQL 聚合。

结论：在 1000 融资 / 5000 结果 / 10000 审计事件规模下，所有交互操作都在 1 秒以内，关键页面在 200 ms 左右。
本版本不做性能重构（冻结架构），以上瓶颈记录为后续优化方向。
